# 聊天体验拼装设计：collector × Warm-Isle × qq-companion-bot

> 版本：v1（设计稿，未实施）
> 日期：2026-11-05
> 前置文档：`docs/Warm-Isle-评估报告.md`（含两仓完整评估与能力矩阵）
> 目标读者：本项目的后续实施者（人或 AI），按 §5 的阶段卡逐期执行

## 0. 决策摘要

**做一个，不是换一个。** 三者是分层互补的，`llm.py` 的生成层与工具层已经比另外两个都强，缺的是**输出节奏、说话时机、记忆贴题、时间感兜底、送达保障**这五样。

- 总改动量：**新增约 800 行 + 修改 6 个文件**，分 5 期，每期独立可回滚
- 预期加权分：**2.50 → ≈4.40**（超过 Warm-Isle 3.81 与 qq-companion-bot 4.09，因为多人辨识 5 分是它们补不上的）
- **不新增顶层配置段**（会打破 `test_llm_bot` / `test_webui_e2e` 的 `["llm","memory"]` 段数断言），新项一律挂现有段
- **不改**生成层：继续用 `llm.build_payload()`（`extra_body` / 三种思考写法 / 三档降级链），不引入 `openai` SDK

## 3. 四个冲突的裁决

> 这一节是本文档的核心。"取各自最好的部分"如果不管这 4 处，拼出来会比现状更差。

### 3.1 记忆只能有一套存储

三套实现互不兼容：

| 来源 | 存储 | 强项 | 问题 |
|---|---|---|---|
| 本项目 | `data/memory/<gid>/people/<uid>.md` + `group.md`，SQLite `chat_log` | 群维度、人可读可手改、已有资产 | 无相关度检索 |
| Warm-Isle | SQLite `memories` 表（`importance`/`confidence`/`expires_at`/`superseded_by`） | 检索 + 衰减 + 冲突合并 | 一对一维度，与群档案语义不通 |
| qq-companion-bot | `memory_long.json`（`who`/`us`/`event` 三桶 + `persona` + `recent`） | 结构最精、条目数配额、淘汰归责清晰 | 仅私聊；JSON 不可手改 |

**裁决：存储留在本项目，另两个只借算法与结构。**

```
存储（不变）
  data/memory/<gid>/people/<uid>.md    ← 人（正文内部改成分桶小节，见 P4）
  data/memory/<gid>/group.md           ← 群概况（不变）
  data/persona/<gid>/heart.md          ← 新增：心事（机器整体重写）
  SQLite chat_log                      ← 素材（不变）
检索（新增，P3）
  运行时把 md 读进内存 → 打分 → 取 top-N 拼块     ← 借 Warm-Isle 的公式
```

**明确否决**：引入 `memories` SQLite 表。理由：等于让两套记忆系统并行，任何一次整理都要写两处、读两处会漂移；且 WebUI 的群记忆页要重做一遍。

### 3.2 「何时说话」只能有一条决策链

现状有三个被动触发点（`__init__.py:765` `@`、`:900` 戳一戳、`:1294` 非音乐链接）加一个定时主动搭话（`banter.py:425 run_banter`），再加概率模型就会出现三重触发。

**裁决：收敛到单一判定入口，`@` 与戳一戳保持恒真。**

```python
# speak.py
def decide_speak(gid: int, kind: str, text: str = "", nick: str = "") -> tuple[bool, float]:
    """返回 (是否开口, 本次概率)。kind ∈ {"at", "poke", "link", "banter"}"""
    if kind in ("at", "poke"):
        return True, 1.0
    p = probability(gid, mentioned=False, text=text, nick=nick)
    return random.random() < p, p
```

决策链（单一顺序，不并联）：

```
@ / 戳一戳 → 恒 True → _llm_answer
非音乐链接 → 概率门 → _llm_answer
banter 定时唤醒 → 概率门 → 免费粗筛 worth_reply → LLM 判官 should_reply → _llm_answer
```

**保留判官**：`banter.py:281 should_reply` 是"免费粗筛 + LLM 复核"，比纯概率准；概率模型只替代"定时器 + 随机间隔"这一层，不替代判官。

概率模型自身的两个铁律（来自其实现，直接照搬语义，代码自行重写）：

1. **先判定、后记账**——否则死群里的第一条消息会先把自己的热度抬上去、把概率打下去，而第一条恰恰最该捧场
2. **自己发言后 `engage` 下降**——否则"越说越有资格说"是正反馈，冷群里会演变成刷屏

### 3.3 拆条只能有一个出口

| 来源 | 规则 |
|---|---|
| qq-companion-bot | **模型用换行自己断句**，最多 10 条，随机 0.5~1.5s 间隔 |
| Warm-Isle | 按标点/长度算法切 1~5 条 + 模拟打字延迟 `min(4000, base+len×35)` ms |

**裁决：模型自控为主，算法兜底为辅，串联不并联。**

```
模型输出
  ├─ 含换行 → 按换行切（模型自己知道哪里是停顿）→ 上限 N 条，超出用「……」合并到最后一条
  └─ 无换行但长度 > 阈值 → 用算法按标点切一次（兜底）
→ 每段：先 clean（去前缀/时间戳），**再**合并超限部分（顺序不能反）
→ 逐条发送，条间随机间隔
```

⚠️ 顺序坑：**先逐条清理再合并**。反过来的话被合并的段开头不再是行首，前缀清理就失效了（这是原实现踩过的）。

⚠️ 与 tool 循环的冲突：带 tools 的轮次里模型可能输出多行结构化内容，**拆条只在"最终回复"出口启用**，不在 `_run_turns` 中间轮次启用。

### 3.4 人设演化有两个方向，别混

| | 本项目 `persona.py` | qq-companion-bot「心事」 |
|---|---|---|
| 改什么 | 改**人设文件** | 不改人设，另存一段"内心" |
| 谁定稿 | 人审（只写 proposals） | 机器整体重写 |
| 作用 | 纠正跑偏 | 情感连续性 |

**裁决：两者都要，分文件、分注入位置。**

```
system 拼接顺序（在现有基础上只加一段，不改原有顺序）
  1. 人设（system_prompt，4000 字上限）
  2. 【心事】                 ← 新增（400 字上限，每轮注入，固定成本）
  3. 群记忆检索块             ← P3 改造
  4. SPEAKER_RULES            ← 不动
  5. TOOL_RULES（硬边界，最后） ← 不动
```

⚠️ **群场景必须重定义 `us` 语义**：原设计是「你和我」（一对一）的称呼/约定；在群里应改成「机器人与这个群」（群梗、群内共识、群规）。否则会写出"我们昨天说好…"这种把某个群友当私聊对象的句子。

⚠️ **时间信息只用一种表达**：不采用"把 `[2026-08-09 19:00 周日]` 塞进每条历史"的做法（模型会照抄，需要额外清洗）；沿用"距上次说话 N 小时"的间隔提示（P5）。

### P1 · 拆条 + 间隔（~80 行，风险最低）

**新文件** `replysplit.py`

```python
def split_reply(text: str, *, enabled: bool, max_parts: int) -> list[str]:
    """模型换行优先；无换行且过长时按标点兜底切分。返回至少 1 段。"""

def between_delay(interval: str) -> float:
    """解析 "0.5-1.5" → 随机秒数；解析失败给 0。"""
```

规则（按序，**已按实现修正**，原稿两处与硬约束冲突）：
1. `enabled` 为 False → **原样一条返回，不清理不切分**。
   ⚠️ 原稿写的是"仍要逐段清理再拼回一条"，与硬约束 #2（关掉时逐字不变）矛盾——
   清理本身就是行为变化。裁决：清理只在打开功能后生效。
2. 按 `\n+` 切，逐段 `clean_part()`：**只**剥行首时间戳方括号（`[2026-11-05 12:30 周三]` / `[12:30]`）。
   ⚠️ 刻意不剥「昵称：」——「注意：」「顺便说一下：」都是合法开头，误删比不删更糟；
   行首 `@昵称` 由既有的 `mention.strip_leading_at` 负责。
3. 超过 `max_parts` → 前 `max_parts-1` 段保留，剩余用「……」合并成最后一段（只合并、不丢内容）
4. 无换行且长度 > 60 字 → 按 `。！？!?~～…` 切；仍只有一段则在第一个逗号处断开（左右各 ≥5 / ≥4 字）
5. ≤6 字的碎片并回前一段——**仅对第 4 步算法切分的结果生效**。
   ⚠️ 实测踩到：若对模型给的换行也回并，「第一句\n第二句\n第三句」会被吞成一句
   （中文一行才 3 个字）。模型断的句是它想好的停顿，必须原样保留。

**改动点**
| 文件 | 改动 |
|---|---|
| `config.py` `LLMConfig` | `reply_split: bool=False`、`reply_split_max: int=10`、`reply_split_interval: str="0.5-1.5"` |
| `__init__.py` `_llm_answer` | 新增 `_split_reply_parts()`：`replysplit.split_reply()` → 每段再过 `bot_utils.split_text()`（传输层长度上限，缺了超长单段会被拒发）；段间 `await asyncio.sleep(between_delay(...))` |
| `config.example.yaml` / `README.md` / `webui.py FIELD_META` | 三项说明（项目约定，缺一不可） |

**验收（`tests/test_reply_split.py`，15 条断言）**
- `enabled=False` → **原样透传**（`split_reply(raw, enabled=False) == [raw]`）
- 3 个换行 → 3 段（模型给的短行不得被回并）；连续多换行算一个分隔
- 15 段 + max=10 → 10 段且最后一段含「……」；拼接后内容无丢失
- 打开时每段开头无 `[2026-` 前缀
- 无换行的长文 → ≥2 段且 `"".join(parts) == 原文`（标点切分不得改动内容）
- 60 字以内不切；末尾碎块并回前一段但保留「嗯。」
- `between_delay`：区间落在范围内、非法/反向/0 区间安全退化

**回滚**：`llm.reply_split: false`（默认即关）。

### P2 · 说话时机（~150 行，需灰度）

**新文件** `speak.py`

状态（进程内，惰性衰减，不跑定时任务）：

```python
_heat: dict[int, dict]   # {"fast": 0..1, "slow": 0..1, "t": ts}
_engage: dict[int, float]
_bot_spoke_at: dict[int, float]
```

```python
def note_group_message(gid)  # 群友之间在聊 → 抬 fast+slow
def note_bot_spoke(gid)      # 机器人发言 → 只抬 fast；engage ×= damp
def note_engage(gid, *, mentioned, text, nick) -> bool  # 被@/紧跟发言/命中关键词
def probability(gid, *, mentioned, text, nick) -> float
def decide_speak(gid, kind, text="", nick="") -> tuple[bool, float]
```

公式（照搬语义，代码自写）：

```
heat   : 边际递减抬升 v += amount*(1-v)，指数衰减 0.5**(dt/半衰期)
p_ambient = p_min + (p_max - p_min) * (1-fast) * (1-slow)
p_engage  = engage_peak * engage
probability = max(p_ambient, p_engage)     # mentioned → 1.0
```

**改动点**
| 文件 | 改动 |
|---|---|
| `config.py` `LLMConfig` | 子段 `speak`（`enabled=False`）+ 12 个参数，见 §6 |
| `__init__.py:190 _listen_group_message` | 每条群消息 `speak.note_group_message(gid)`；`note_engage(...)` 返回值决定是否只抬 engage 不抬 heat |
| `__init__.py` 三个触发点 | `@`/戳 → 直接放行；`link` → 过 `decide_speak` |
| `__init__.py:_llm_answer` 成功后 | `speak.note_bot_spoke(gid)`（与 `banter.note_reply` 并列） |
| `banter.py:425 run_banter` | 定时唤醒后先过 `decide_speak(kind="banter")`，再 `worth_reply` → `should_reply` |

**验收（`tests/test_speak.py`，纯函数，无网络）**
- 冷群（heat=0）→ p ≈ `p_max`；刷屏群（fast=slow≈1）→ p ≈ `p_min`
- `mentioned=True` → 1.0，且不走 ambient/engage 计算
- **判定先于记账**：连续两条冷群消息，第一条的 p 必须高于第二条（因为第二条前已记账）
- 发言后 `engage` 下降；`note_bot_spoke` 只抬 `fast` 不动 `slow`
- 紧跟发言窗口只生效一次（用完即清）

**灰度**：`speak.enabled=true` 但 `speak.dry_run=true`，只把 `p` 写进日志与 `llmtrace`，**不改变是否发送**，观察 3~7 天后再真正接管。

**回滚**：`llm.speak.enabled: false`。

### P3 · 记忆检索（~90 行，低风险）

**改** `memory.py`：在 `render_for_prompt`（`:516`）内部、装人之前插一层打分。

```python
def score_person(person, tokens, now) -> float:
    """相关度×0.5 + 重要度×0.3 + 新鲜度×0.2"""

def tokenize(text: str) -> set[str]:
    """中文二元组 + 英文数字整词（『我昨天加班到十点』→ 我昨/昨天/天加/加班/…）"""

def pick_people(mem, group_id, query, *, top, min_n, chars) -> list[Person]
```

规则：
- **相关度**：query 的 token 被 `person` 正文覆盖的比例 ×2.2（封顶 1.0）；姓名/别名命中额外 ×1.4
- **新鲜度**：`exp(-ln2 * days / 30)`（半衰期 30 天）
- **重要度**：优先用档案里的手工标记，缺失取 0.5
- **无命中回退**：最近活跃的 N 人（= 现状行为），保证"退化后不更差"
- **群概况必带**（不参与打分），末尾仍写"还有 X 人未展开"（现有行为保留）

**改动点**
| 文件 | 改动 |
|---|---|
| `memory.py:516 render_for_prompt` | 装人循环前插 `pick_people`；新增 `query` 参数（默认 `""` → 走旧逻辑） |
| `llm.py:1086 chat` | 把当前提问 `text` 传进 `mem_text` 的组装处 |

### P4 · 记忆结构：三桶 + 心事 + 条目配额（~350 行，改动最大）

**这一步只做"结构与整理"，不改注入算法（P3 已改）。**

**`digest.py:31 DIGEST_SYSTEM` 重写为三桶产出**（语义自写，判据借用）：

| 桶 | 回答什么 | 判据 | 不记什么 |
|---|---|---|---|
| `who` | 这个人是什么样的人 | 半年后依然为真，且只关于他 | 他说过什么、答应过什么 |
| `us` | 他与这个群/与机器人的关系状态 | 描述状态，不是单次的事，不带日期 | 带日期的事 |
| `event` | 有确定时间点的事 | 能说出"哪天" | 日常琐事 |
| `recent_new` | 最近几天的日常（只给新增） | 有具体内容 | 寒暄、已有流水 |

要点（全部来自踩坑记录，逐条照搬结论）：
1. **按条目数而非字数配额**——用字数会出现"模型按整段 JSON 估、代码只数正文"的 7~9 倍偏差，模型以为额度不够 → **把整库输出成空数组**
2. **`us` 用状态口吻，不用债务口吻**——"他答应每天说喜欢我"会变成还不完的欠条
3. **时间点写进句子，不另设 `exp` 字段**——模糊时间（"过阵子"）填不出日期，会变成永不失效的幽灵事件
4. **淘汰归责**：语义性淘汰（取代/合并）交给模型；时间性淘汰（`recent` 按天滚动）交给代码
5. **整库重写必须加"覆盖防护"**：条目数不足既有一半 → 告警且用 `.bak` 回滚
6. **同一会话只许一次整理在跑**（"压缩中"标记覆盖整个压缩过程，含锁外两次 LLM 调用）

**新文件** `heart.py`：「心事」生成（独立一次角色内省调用，走 `llm.complete()`）
- 输入：人设 + 现有心事 + 关系现状 + 最近对话
- 明令"延续不是重来"（否则每次重写成另一个人）
- 输出 400 字上限，**整体重写**，写 `data/persona/<gid>/heart.md`
- 素材不足（< 10 条）→ 不调模型，保留旧心事
- **群场景适配**：心事主体是"我在这个群里是谁"，不是"我和某个人的关系"，提示词必须写清

**改动点**
| 文件 | 改动 |
|---|---|
| `digest.py` | 产出三桶；`parse_reply` 兼容旧扁平格式；`.bak` 备份；条目配额校验 |
| `memory.py:174 parse_person` / `:156 dump_person` | 正文支持 `## 他是谁` / `## 我们之间` / `## 事件` 三节；**旧格式自动迁移**（读到无小节的正文 → 原样塞进"事件"或保留为未分区，向前兼容） |
| `memory.py:516 render_for_prompt` | 在第 2 位插入心事块（人设之后、记忆之前） |
| `heart.py` 新 | `build()` / `render()` / `read()` / `write()` |
| `scheduler.py` | 心事任务的触发时机（可复用现有 `style` 任务的调度模式） |
| `config.py` `MemoryConfig` + `PersonaConfig` | 配额与心事参数 |
| `webui.py` 群记忆页 | 三桶展示 + 心事只读预览 + 一键 `.bak` 回滚 |

**验收（`tests/test_heart.py` + `tests/test_digest_buckets.py`）**
- 旧格式档案读进来 → 不抛异常、不丢内容、可再写回
- 一次 digest 后：三节齐全、总条目 ≤ 配额、每桶 ≤ 桶配额
- 模型返回空数组 / 不足一半 → 告警 + `.bak` 回滚，**库内容不变**
- 返回非法 JSON / 顶层非对象 / 代码块包裹 → 跳过本次，库不变
- 心事素材 < 10 条 → 不调模型（用桩断言零调用）
- 心事超 400 字 → 截断而非报错

**回滚**：`memory.buckets_enabled: false` → 回退"整段正文"模式（保留旧 `.bak`）。

### P5 · 兜底三件套（~140 行）

**5.1 送达回执才落库（最便宜、最该先做）**

现状：`llm.py:1375` 在 `chat()` 内部、**发送之前**写 `chat_log`。发送失败时模型已经"记得自己说过"，后续会等一个不会来的回应。

改法（最小侵入，不动 `chat()` 返回签名）：
1. `chat(..., persist=False, body_out: dict | None = None)` —— 不写库，把要写的两行内容回填到 `body_out`
2. `bot_utils.safe_send_group` 改为返回 `dict | None`（拿到 `message_id`；真值语义兼容现有调用）
3. `_llm_answer` 在 `parts` **全部发送成功**后调 `llm_bot.persist_turn(...)`；任一段失败 → 不落库 + 警告日志（部分成功则只落库成功的那几段）

**5.2 TimeGuard**

`timeguard.py`：`fix(text, now) -> text`
- 仅 06:00–20:00 生效（夜间不拦）
- 正则命中 `晚安|今晚|大晚上|这么晚|早点睡|该睡了|睡吧|梦` → `llm.complete()` 低温暖改写一次（`thinking="off"`、不占冷却、不写历史）
- 改写结果仍含夜间词或为空 → **词表硬替换**（`今晚→今天`、`晚安→回头聊`、`早点睡→早点休息`、`该睡了→别太累`）
- 挂在 `_llm_answer` 拿到 `reply` 之后、拆条之前

**5.3 预算闸门**

`llmtrace.py` 已有每次 `usage`（`prompt_tokens` / `completion_tokens`），加：
- 当日累计 × 单价（`llm.price_in` / `llm.price_out`）→ `spent_today`
- `_llm_gate` 加一道门：`spent_today >= llm.daily_budget`（`<=0` 视为不限）→ 返回 `"今日预算用尽"`，走不花钱路径
- 兜底话术不暴露原因（"我这会儿有点卡，等下再回你哈"）

**改动点**
| 文件 | 改动 |
|---|---|
| `llm.py` | `persist` 拆分 + `body_out` + `persist_turn()` + 挂 TimeGuard |
| `bot_utils.py` | `safe_send_group` 返回回执 |
| `__init__.py:335 _llm_gate` | 预算门 |
| `llm.py` / `config.py` | `daily_budget`、`price_in`、`price_out`、`time_guard` |

**验收（`tests/test_delivery.py`）**
- 发送桩返回失败 → `chat_log` 无新增（对比调用前后行数）
- 发送桩返回成功 → 两行都写入且内容与旧实现一致
- 部分段失败 → 只写入已送达的段
- 白天 `晚安` → 被改写；夜间不拦；改写失败 → 词表兜底
- 超预算 → 不进模型、走回退话术、日志有记录
