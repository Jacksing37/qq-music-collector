# QQ 群音乐分享收集机器人

自动识别群里分享的网易云 / QQ 音乐 / 酷狗 / 酷我 / 汽水音乐 / Apple Music 等链接和卡片，@ 分享者并回发歌曲名片，按时间顺序整理榜单（文字 + 长图），并在设定时刻自动归档到网易云歌单。归档后的歌单**自动写入简介**（开头模板 + 「谁分享了什么歌」清单，一首一行）。

## 功能特性

- **自动识别**：链接 / JSON 卡片 / XML 卡片 / 短链跳转，含 QQ 音乐 mid、网易云数字 id 等
- **即时反馈**：识别后 @ 分享者并回发歌曲名片（卡片失败三级降级，信息不丢）
- **榜单整理**：文字 + 长图，按发送先后排序，支持中文标题渲染
- **定时归档**：到设定时刻在网易云新建歌单并加入全部歌曲，歌单名与简介均可自定义
- **同窗口复用追加**：同一窗口归档过一次后再次归档（如手动 `/music archive` 补发），会**复用已有歌单追加新歌**，不会重复建歌单、不消耗期号
- **分享即归档**：可开 `auto_archive_on_share` 开关，每收到一批新歌立即自动追加进当前窗口歌单（静默执行，结果只记日志）
- **简介自动生成**：开头模板 + 逐首「X 分享《歌名》- 歌手」或按人聚合，一首一行，超 1000 字自动截断
- **表情安全**：昵称 / 歌名里的 emoji 自动转中文词，绕开网易云简介 utf8(3 字节) 存储限制
- **掉登录自动重登**：`MUSIC_U` 过期（写接口报 `code=301`）时自动续期 / 用手机号密码重登并重试，不用再手动粘贴 cookie；被**写接口频控**（`code=405` 操作频繁）时不瞎重登，直接入队等定时补写
- **未识别不入榜**：解析失败的链接不会污染榜单，仅给分享者一条轻量提示
- **无法匹配当场提示**：非网易云来源的歌搜不到时，直接在「已收录」同一消息里附提示（`reply.unmatched_text` 可自定义），不用等归档报告
- **引用提示即可手动匹配**：引用那条「没法匹配」的提示消息 + 贴网易云链接，分享者本人或管理员就能把歌绑定上去（`playlist.reply_match`）
- **每人本期只收一首**：`playlist.one_per_sharer` 开启后，同一窗口内同一用户只收录第一首，其余回可自定义提示（`reply.sharer_limit_text`）
- **未匹配标注分享者**：归档时没能匹配到网易云的歌曲，会在简介与归档结果里附上「分享者 - 歌名」
- **被 @ 即自我介绍**：任何时候 @ 机器人都会回应，文案可自定义（支持占位符 + 冷却）
- **@ 机器人可聊天（大模型）**：开启后 @ 机器人说一句话（非音乐链接、非 `/music` 命令）就由大模型回答，可在网页端「机器人」页配置接口地址 / Key / 模型 / 人设 / 上下文轮数 / 冷却，并指定生效群；**被戳一戳**、**分享了不是音乐的链接**也会接话；能读**引用内容、图片、合并转发的聊天记录**，还能**自己调用工具**（需要时用 `fetch_url` 抓网页正文、按技能包里的步骤做事）；失败自动退回自我介绍。**该页设置只能在网页端改，群内无任何命令可读写**
- **群记忆（记住每个人）**：机器人旁听群聊（只记录、不回复），每隔几小时把「谁是什么样的」整理成**每人一份 markdown**（`data/memory/<群号>/people/<QQ号>.md`，可直接编辑），聊天时自动带上；模型也能主动 `remember` / `recall` / `forget`。上下文同时**落库**，重启不丢。详见「群记忆」章节
- **手动开关收集**：`/music collect on|off` 临时覆盖时间表，方便随时测试
- **全时间可配置**：每周 / 每日 / 单次，星期与时刻均可改，群内命令即时生效，撞点自动去重
- **分享者昵称映射**：可在网页端「昵称映射」独立页设置 `原昵称=显示名` 或 `QQ号码=显示名`（如 `菜老名=Jacksing` 或 `123456789=Jacksing`），网易云简介 / 群内文字榜单 / WebUI 表格里的分享者名字都会替换成显示名，但数据库仍保留原始昵称（昵称优先于 QQ 号码匹配）
- **总库（跨窗口去重）**：开启后每首新分享会同时进入群级「总库」，跨窗口去重；分享已存在于总库的歌会提示重复（仅跨窗口，与同窗口「重复提醒」互不冲突；**绝不会静默吞掉分享**），提示文案 `master.notify_template` 支持 `{date}`/`{who}` 等占位符——从歌单导入进总库的歌没有分享者信息，会显示成「未知（总库导入）」。总库可在网页端独立增删改 / 拖拽排序 / 同步到歌单，并独立归档成一个大歌单，功能与正常收集一致

## 技术栈

- 框架：[NoneBot2](https://github.com/nonebot/nonebot2) + OneBot v11
- 协议端：[NapCat](https://github.com/NapNeko/NapCatQQ)（推荐）/ Lagrange.OneBot
- 存储：SQLite（零部署）
- 渲染：Pillow（无需浏览器）
- 调度：APScheduler（`nonebot_plugin_apscheduler`）

## 快速启动

### 1. 准备 NapCat

配置 QQ 号，反向 WebSocket 指向本机器人：

```json
{ "url": "ws://127.0.0.1:8080/onebot/v11/ws" }
```

### 2. 配置环境

```bash
cp .env.example .env
# 编辑 .env，至少配置 SUPERUSERS（超管 QQ 号），建议设置 MUSIC_WEBUI_TOKEN
```

### 3. 安装依赖并启动

```bash
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python bot.py
```

首次运行自动把 `config.example.yaml` 复制为 `data/config.yaml`，之后用群内命令修改即可，无需重启。

> 依赖装漏 `nonebot-plugin-apscheduler` 会在启动时报 `ModuleNotFoundError`。
> 注意始终用 `.venv\Scripts\python`，别用系统 Python。

### 4. 网易云登录（建歌单必需）

1. 浏览器打开 https://music.163.com 并登录
2. F12 → Network，刷新页面，找任意 `music.163.com` 请求
3. 在请求头 Cookie 中找到 `MUSIC_U=xxxxx`
4. **私聊**机器人发送：`/music cookie xxxxxx`

> ⚠️ `.env`、`data/`（含 `config.yaml` / `group_overrides.yaml` / `collector.db` / `netease_session.json`）均已被 `.gitignore` 忽略，切勿提交，否则账号凭证会泄露。

#### 掉登录自动重登（可选，推荐）

网易云的 `MUSIC_U` cookie 会过期、也会被风控，失效后**所有写接口统一返回 `code=301`「需要登录」**，表现就是「歌单简介一直写不上去」。

开启后（配置页「网易云登录」分组，或 `data/config.yaml`）：

```yaml
netease:
  auto_relogin: true          # 掉登录自动重登（默认开）
  phone: '13800000000'        # 登录手机号
  password: '你的密码'         # 或改填下面的 md5，避免明文
  password_md5: ''            # 密码的 32 位 hex md5
  countrycode: '86'
  relogin_cooldown: 300       # 两次自动重登的最小间隔（秒），防风控期狂试
```

写简介失败时会按**失败码归因**再决定怎么办：

| 失败特征 | 含义 | 处理 |
|---|---|---|
| `code=301` 需要登录 | cookie 已过期（真掉登录） | 先 **cookie 续期**（`/login/token/refresh`，不需要密码），不行再用 **手机号 + 密码**重登（`/login/cellphone`），然后**自动重试一次** |
| 连 `linuxapi` 通道也回 `code=405` 操作频繁 | **写接口的账号级频控**（`eapi`/`api` 回 405 是常态，这两条通道本来就写不进简介，不算数） | **不重登**（换 cookie 治不了频控），直接入队交给 `job_descfix` 隔一段时间补写 —— 频控是「等」出来的，不是「重试」出来的 |

> 为什么要区分这两种？2026-10-10 在线上实测确认：① 同一个 cookie 在 16:23:35 刚用 `linuxapi`
> 写成功另一个歌单，4 秒后写第二个就 405 —— 与登录态无关；② `eapi` 续期返回 `code=200` 但
> **不下发新 cookie**（指纹前后一模一样），拿它当「重新登录」是自欺欺人；③ 若服务器 IP 被网易云
> 判为风险网络，账密登录会直接被拒（`code=8810 您当前的网络环境存在安全风险`）。

**8810 的人工验证**：撞风控时网易云会在响应里带一个 `redirectUrl`，指向网易易盾的风控验证页
（`https://y.music.163.com/g/yida/<token>`）。**它不会给手机推短信验证码**——要解锁必须在真实浏览器
里打开这个链接，走一遍人机验证（视风险等级可能给滑块，或页内再让你手机号+验证码）。本 bot 会把这个
链接**原样挖出来展示**：日志里打一条 `[netease] 账密登录被风控拦截……请在浏览器打开以下链接`，
配置页「网易云登录」分组也会把链接渲染成可点链接。过完验证再点一次 **重新登录** 即可。若验证仍过不去
（例如服务器的 IP 与打开链接的 IP 不同），最终仍可**手动粘贴新的 `MUSIC_U`**。

新下发的 cookie 写在响应头的 `Set-Cookie` 里，所以 **weapi / eapi / linuxapi / api 四条通道都会
吸收并落盘**到 `data/netease_session.json`（重启后仍有效）。日志与配置页都会给出一个 `cookie 指纹`
（`MUSIC_U` 的短哈希），用它就能一眼确认「重登后 cookie 到底换没换」：

```
[netease] 账密登录成功（weapi），cookie 指纹 8ea79b53     ← 指纹变了，说明真换了
[netease] 账密重登未成功（code=8810 您当前的网络环境存在安全风险），改试 cookie 续期兜底
[netease] 续期成功，但注意：续期通常**不下发新 cookie**，指纹仍为 a6ff48a6
```

在配置页「网易云登录」分组点 **重新登录** 时，会优先尝试账密换一套全新 cookie（跳过「原地续期」），
并直接告诉你指纹有没有变。

- 只填 `phone`/`password`（或 `password_md5`）才会启用账密重登；不填则只做 cookie 续期。
- 网页端配置页的**「网易云登录」分组**里有 **重新登录** 按钮，可手动触发一次（忽略冷却）。
- 不想用就设 `auto_relogin: false`，回到旧行为（失败只记日志 + 入队等定时补写）。
- ⚠️ 配置文件里存的是账号凭证，请确保只有自己可读：`chmod 600 data/config.yaml`。

> 若开了二步验证 / 频繁异地登录，网易云可能拒绝账密登录（`code=8810`），此时先在配置页给出的
> **人工验证链接**里过一遍易盾验证，再点「重新登录」；仍不行则手动粘贴新的 `MUSIC_U`。

## 群内命令

不带参数发送任意命令即可看到它自己的详细用法。完整清单见 `/music help`。

```
【所有人】
/music list          本期榜单（文字 + 长图）
/music count         已收集数量
/music window        时间窗口配置与下次触发
/music status        运行状态 / 网易云登录状态
/music preview       预览本期歌单名

【管理员 · 时间】
/music mode weekly|daily|once                切换循环模式
/music set time <开始>-<结束>                 一键设：开始-结束（汇总/归档统一=结束）
   例: /music set time 周五 12:00-周五 20:00

/music seq <数字>                  期号（/music seq auto on|off 开自动递增）

【管理员 · 音乐卡片】
/music card                        查看卡片模式与熔断状态

/music parse <链接>        诊断链接为何没被识别
/music debug on|off       识别过程详细日志
```

### 时间点格式

- weekly: `MON 20:00` 或 `周一 20:00`
- daily : `23:00`
- once  : `2026-08-10 00:00`

## 配置管理 Web UI

不想记命令？内置了一个网页配置面板，打开浏览器就能改所有设置。

- **访问地址**：`http://<机器人IP>:8080/music-admin`（与 OneBot 共用 8080 端口，路径不同）
- **进入令牌**：在 `.env` 里设 `MUSIC_WEBUI_TOKEN=你的令牌`；
  若没设，机器人启动时会**随机生成并打印在日志里**（每次重启都变，建议固定下来）。
- **功能**：按分组（通用设置 / 网易云登录 / 收集时间窗口 / 歌单与简介 / 音乐卡片策略 /
  长图渲染 / 缓存清理 / 歌曲记录清理 / 自我介绍 / 收录回复模板 / 总库 / 运行日志）渲染表单，
  支持暗/亮主题切换，顶部实时显示当前收集状态与下次定时；保存即生效，
  **改时间窗口会自动重载定时任务**。网易云登录排在「通用设置」之后，
  手机号 / 密码 / 掉登录自动重登 / 重登按钮 / 粘贴 cookie 都在同一个分组里。
- **自动同步**：表单由 `config.py` 的 pydantic 结构**自动生成**（嵌套子模型也会递归展开），
  以后加配置项 UI 会自动出现，无需改前端。
- **按群独立配置**：配置页顶部有个**配置对象**下拉——「全局默认（所有群）」或某一个群。
  选到某个群时，看到的是该群**真正生效**的值（全局默认叠加该群的覆盖），
  被本群单独改过的项会**高亮并标注「本群自定义」**，未改过的项灰显标注「继承全局」，
  右侧还有一个 **↺ 继承全局** 按钮可随时撤掉那一项的本群值；顶部「全部恢复继承」一次撤掉全群覆盖。
  改哪些项就只为该群记一条覆盖，其余全部跟着全局走——**改全局默认会立刻穿透到所有没单独设过的群**。
  - 覆盖项存在 `data/group_overrides.yaml`（只记被显式覆盖的点分键），
    与该群无关的群不会多出一条记录；把某个群的覆盖清空后，该文件里对应段也会被删掉。
  - **期号是共享的**：只有该群**单独设过**期号时，归档自增才写该群；没设过的群共用全局那一份计数器，
    不会被拆成一堆互不相干的数字。
  - **收集时间窗口可以按群不同**：某个群单独改过 `window.*`，就会为它注册一套独立定时任务
    （`music_collector_<任务>_g<群号>`），并从全局任务的处理列表里摘出去，避免同一时刻播报两次。
  - **进程级唯一的设置不能按群覆盖**：日志缓冲、缓存清理、网易云账号、字体路径、
    生效群号（`groups`）、识别调试日志、歌曲记录定时清理 —— 这些在「按群」视图里会灰掉并注明
    「进程级设置，始终取全局值」；即使带群号提交也会落到全局，不会存下一个永远不会生效的值。
- **总库管理页**：面板左侧「📚 总库」进入，按群展示该群总库歌曲（与收集管理页同样的编辑 / 拖拽排序 / 匹配 / 增删 / 同步 / 归档能力），每个群卡片附其总库歌单链接；顶部「汇总现有窗口到总库」可一键把历史各窗口歌曲回填进总库。总库相关开关（是否启用、分享是否对比、重复提示文案、归档模板等）在「⚙ 配置」的「总库」分组里设置。
- **昵称映射独立页**：面板顶部「✏ 昵称映射」按钮（或直访 `http://<机器人IP>:8080/music-admin/aliases`）
  打开一个专页，每行写一条 `原昵称=显示名`，带实时预览；保存后网易云简介、
  群内文字榜单、WebUI 表格里的分享者名字都会替换，仅做展示，不改入库。
- **运行日志页**：面板左侧「📜 运行日志」进入，直接看机器人日志，不用再 SSH 上去翻
  `journalctl`。支持**来源筛选**（🤖 只看机器人 / 协议端 / uvicorn）、**级别筛选**、
  **关键词搜索**（消息 / 模块名 / 异常堆栈都能搜）、**3 秒自动刷新**（原来就停在底部才自动跟随）、
  **一键复制**、**清空缓冲**；报错条目会连堆栈一起展开显示。

  服务器上日志的大头是协议端（`nonebot`：OneBot 适配器的每条群消息 / 事件分发）和
  `uvicorn`（网页请求访问日志），所以**默认建议把「来源」切到 🤖 只看机器人**——
  这样看到的就是机器人自己干了什么：

  ```
  [config] 修改 playlist.seq: 94 → 95
  [music] 收集开关 → 已手动开启收集（无视时间窗口）
  [music] ← 群1053096807 张三(10001): https://music.163.com/song?id=123
  [music] 分享处理 · 群1053096807 张三(10001) · 收录 1 / 同窗重复 0 / 已分享过 0 / 未识别 0
  [music] → 群1053096807 [@] 已收录 · 本期第 3 首 …
  ```

  改设置（网页端 / 群内 `/music` 命令都会）、手动开关收集、收到与发出的消息、
  归档与同步结果都会留痕；密码类配置写入时自动打码。

  机器人（大模型）相关的事件也在同一页，搜 `[llm]` 就能筛出来：

  ```
  [music] ← 群1053096807 张三(10001): @机器人 这首歌谁唱的
  [llm] 群1053096807 张三(10001) 提问 9 字 → 回复 42 字（model=gpt-4o-mini）
  [llm] 群1053096807 张三(10001) 冷却中（还剩 25s / 共 60s）→ 静默跳过
  [llm] 群1053096807 未走大模型：群 1053096807 不在生效列表（当前 2 个群）
  [llm] 群1053096807 生成失败: HTTP 401: Invalid API key
  [llm] 群1053096807 上下文超窗（丢弃 6 条 / 1200 字）→ 不带历史重试
  [llm] 测试连接成功（model=gpt-4o-mini，820 ms，回复 36 字）
  ```

  排查「@ 了没反应」按这个顺序看：先有没有 `[music] ←`（没这条就是消息没进来）→
  有没有 `未走大模型：…`（配置没生效，这种默认记 INFO，直接可见）→ 有没有
  `冷却中` / `生成失败`。命令消息、音乐分享、只 @ 不说字属于正常分流，只记 **DEBUG**
  （把 `logs.level` 临时调成 `DEBUG` 才看得到），免得把日志页刷满。

- **🧠 LLM 调用记录**：把「来源」切到 **🧠 LLM 调用**，日志区域会换成另一套视图——
  **每次问答一条、点开看详情**，比在文本日志里拼凑强得多：

  | 看什么 | 里面有什么 |
  |---|---|
  | **提问** | 完整的一句话，带 `昵称(QQ号)：`（连引用内容、资料前缀都在） |
  | **经过** | 每一步：`📦 system 369 字（其中记忆 469 字）/ 历史 40 条 1488 字 / 工具 6 个`、`🔧 调 fetch_url(…) → 返回 1200 字`、`↩️ 超窗，丢弃 6 条后重试`、`⏳ 冷却中，没走到模型` |
  | **回复** | 模型输出的全文 |
  | **思考** | 开了思考模式时的 `reasoning_content` |
  | 抬头 | 群号、谁问的、**耗时**、成功/失败（失败标红并写出原因） |

  它**不走**上面那套文本日志：那边一次问答要摊成十几行、还混在 nonebot / uvicorn 的
  刷屏里；而且插件内的 stdlib logger 经 NoneBot 归一后名字都叫 `music_collector`，
  按 logger 名根本分不出 `llm`。所以这里是单独的一份**结构化**记录（`llmtrace.py`，
  内存环形缓冲，默认留最近 200 条），字段分开存、前端折叠展示。同样只含本次启动后，
  「🗑 清空」在这个来源下清的是它自己。

  排查「它答得不对」时最有用的就是**经过**那一栏：能直接看出是没进模型（冷却 / 群不在
  生效列表）、还是工具调了但没拿到东西、还是超窗后丢了历史。

  日志来源是进程内的**环形缓冲**（NoneBot 把日志打到 stdout，服务器上由 systemd 收进
  journald，进程里读不到；Docker 里则只有 `docker logs`），所以**只含本次启动后的日志**，
  重启即清空。想跨重启留存就把配置页「运行日志」分组里的 `logs.file` 填成路径
  （如 `data/logs/bot.log`，按 5MB 轮转、保留 3 份）。

  | 配置项 | 默认 | 说明 |
  |---|---|---|
  | `logs.lines` | `2000` | 内存里保留的条数（50~200000），满了丢最旧的 |
  | `logs.level` | `INFO` | 记录的最低等级；排查问题时临时降到 `DEBUG`（页面筛选取不到没被记录的日志） |
  | `logs.file` | 空 | 额外落盘路径（相对路径基于项目根目录）；留空 = 不写文件 |
  | `logs.trace_messages` | 开 | 记录**收到 / 发出的群消息**摘要（含普通聊天）。只想看开关收集 / 改设置 / 归档结果就把这项关掉 |
- **配置分组跳转栏**：配置项多、页面长，配置页顶部有一条**分组跳转栏**，点「歌单与简介」
  之类的按钮直接滚到对应分组，滚动时当前分组会自动高亮。往下滚时这条跳转栏会**吸在顶部跟着走**
  （贴在顶栏与「配置对象」条下面），不会滚着滚着就找不到了。
- **手机端适配**：面板在手机上也能用——侧边栏变成顶部可横向滑动的导航条，
  配置项改成标签在上、控件在下，表格可横向滚动，底部保存条占满宽度，
  日志页与预览抽屉同样适配。**「收集管理」「总库」里的群卡片在手机上默认按群折叠**，
  只显示群标题与歌曲数，点哪个群就展开哪个（同时收起同页其它群）；
  从「概览 → 各群收集概览 → 去管理 →」进来时，会自动展开目标群并滚到它。

### 机器人设置（@ 机器人 → 大模型回复）

侧边栏 **🤖 机器人** 页是独立的一页，只放「大模型回复」相关设置。

**触发条件**：群里 **@机器人 + 一句话**，且这条消息

- 不是 `/music`（或 `音乐`）命令；
- 不是**能识别的音乐**链接 / 卡片（那种照旧走收录流程；注意判定是「真音乐链接」，
  不是「带 http 就算」——所以 @ 机器人 + 一个普通网页链接现在也会让模型答）；
- 消息里确实有内容（文字 / 图片 / 引用，三者有其一；只 @ 一下不触发）。

另外一种场合也会让模型开口（仍受总开关、生效群、冷却约束）：

- **戳一戳**：群友双击头像戳机器人，回一句（`llm.poke_reply`）；私聊戳不接。

至于「分享的不是音乐链接」，**默认不主动接话**——群里甩一个网页 / 视频 / 文章链接时，机器人一声不吭；
想要它回答就 @ 一下。老版本那种「任何链接都主动接一句」的行为还留着，把 `llm.reply_link` 打开即可
（真·音乐链接永远不会被这条截走；@ 了的那条由 @ 流程回答，不会回两遍）。

**最后一种是「没人叫它也说」**：`llm.banter` 打开后，非勿扰时段里每隔一段随机时间
（`llm.banter_minutes`，默认 `30-60` 分钟）重新抽一个时间点，把群里**上次搭话之后**聊的
那一段接过去，**不 @ 人、不引用**。素材取自群记忆的旁听记录，所以 `memory.listen` 也要开着。

- **素材是一段而不是一条**：从上次搭话处理到的位置（`chat_log.id` 游标）往后取，
  所以它看到的是「这段时间发生了什么」，接的是话题而不是机械附和最后一句。
  一次最多看 `llm.banter_batch_max` 条（默认 40）/ `llm.banter_batch_chars` 字（默认 6000，
  超了从最旧的丢）。游标同时也修掉了「同一句被接两次」。
- **判官先判断该不该插嘴**（`llm.banter_judge`，默认开）：吵架、严肃话题、别人正在对话、
  对话已经收尾……它说不该就闭嘴。判定标准写在 `llm.banter_judge_hint` 里，**网页上直接改**
  （不同群尺度不一样），留空用内置清单。判不出来（接口报错、回一堆废话）**一律按不接**——
  静默最多是少说一句，接错话是社死。
- **被动回复完重新计时**（`llm.banter_reset_on_reply`，默认开）：它刚 @ 回完一句，计时就
  从那一刻**重新起算**，间隔仍取 `banter_minutes`。不这样的话，它 22:00 刚答完人、
  22:01 又被排到的那一轮捞起来自己冒泡，群里看着就是抢话；而且刚说完那一两句，
  可接的素材也还没跟上。定时任务会跟着挪到解禁之后再跑，不白跑一轮。
- **勿扰时段** `llm.banter_quiet` 可配**多段**（`00:00-08:00, 12:00-14:00`），支持跨午夜
  `23:00-08:00`。落在段里的那次会**顺延**到该段结束后再随机 0~10 分钟——不是"到点发现是勿扰就跳过"，
  那样夜里会每半小时空转一次，白天的节奏也跟着漂。
- **批次里最后一条太旧就不接**（`llm.banter_fresh_minutes`，默认 20 分钟）：半夜突然接一句
  两小时前的话，比不说话还怪。判的是最后一条而不是第一条——聊了半小时的对话，
  只要刚还在继续就还值得接。
- **太短 / 纯标点 / 命令**不接（"嗯"、"？？？"、`/music list` 接起来没意义）；整批都够不上就跳过。
- **每群每天上限** `llm.banter_daily_max`（默认 `0` = 不限，约 20 次/天）。这是控制吵不吵**最有效**的旋钮：
  间隔决定节奏，上限决定总量，觉得吵就直接填 `4`。
- 这一路**不占被搭话者的冷却**（否则他紧接着 @ 机器人会被静默），**不带工具**（不联网、不写记忆，
  也省掉 900 token 的工具 schema），历史只带最近 12000 字——主动冒泡不该背着百万字上下文花钱。
- 判官说「不接」时**也会推进游标**，否则下一轮还是这批消息、判官还说不接，会死锁在反复白跑。
  日志里两者分得清：`决定不插嘴`（识相）vs `没有素材`（确实没人说话）。

命中后由大模型生成回复；**不命中或调用失败**时仍然走原来的内置自我介绍
（`llm.fallback_intro` 关掉则失败时静默）。大模型与自我介绍**互斥**，不会一次发两条。

| `llm.banter_judge_chars` | `2000` | 判官最多看多少字（只取最近的） |
| `llm.banter_reset_on_reply` | 开 | 被动回完一句就把搭话计时重新起算（免得刚答完又自己冒泡） |

> 📏 **系统提示词有硬上限 4000 字**：超出的部分会被直接截掉（日志里会留一条 WARNING）。
> 网页端输入框下面会实时显示「已用 3821 / 4000 字」，超了变红——写到差不多就该收手了。

页面上还有两个按钮：**🧪 测试连接**（按已保存的配置发一条最小请求，直接看模型回什么、耗时多少）
和 **🧹 清空上下文**（清掉内存里缓存的对话）。

> 👀 **群友发的图 / 引用，模型能看到吗**：能，但分程度。
> - **文字**：原样送过去。
> - **引用回复**：把被引用的那条压成一句 `（引用 张三 的消息：xxx）` 放在提问前面，长度由 `llm.reply_chars` 控制。
> - **图片**：默认只在文字里留 `[图片]` 标记——模型知道对方发了图，但看不到内容。想让它真看图，
>   把 `llm.vision` 打开并换一个**视觉模型**（qwen-vl-max / glm-4v / gpt-4o 这类）。
>   打开但模型不吃图时，程序会**自动去掉图片重试一次**，群里不会看到报错。
> - **被引用消息里的图片**：会一起发过去（`read_reply` 开着才会读引用）。额度由 `llm.max_images` 统一切，
>   **当前这条消息的图优先**，剩余的才轮到引用的图；同一张图不会重复发。
>   所以「引用别人一张图，问『什么意思』」现在模型真能看到那张图——以前只给 `[图片]` 占位符，
>   模型会回一句「图我这边没瞅见」。
> - **转发的聊天记录里的图片**：同样会一起发（额度还是 `llm.max_images`，排在当前消息和引用的图之后）。
>   记录里的文字仍带 `[图片]` 占位，图片本体作为图片发过去——「转发一段带图的聊天，问这图啥意思」才答得上。
> - **只引用不说话也算一句话**：引用别人一条消息、只 @ 机器人不写别的，会照样交给模型（它有被引用的内容可读），
>   以前这种情况会被当成「什么都没说」退回自我介绍。
> - **表情 / 语音 / 文件 / 视频**：只留 `[表情]` `[语音]` `[文件: xxx.mp3]` 这类标记，不做内容识别。
> - 只发图、一个字不打也能触发（直接 @ 机器人 + 发图）。
>
> 图片链接**不进上下文历史**（历史里只记 `[图片]`）：QQ 图片链接几小时就过期，存着既没用又白占预算。

|---|---|---|
| `llm.read_forward` | 开 | 展开「转发的聊天记录」给模型看（关掉时它只看到 `[聊天记录]` 四个字） |
| `llm.forward_limit` | `30` | 一次最多展开几条转发消息 |
| `llm.forward_chars` | `2000` | 转发内容总字数上限，超出会标出「还有 N 条未展开」 |
| `llm.bg_chat` | `true` | 被动回答时带上「机器人上次说话之后」的群聊背景（详见下文） |
| `llm.bg_chat_max` | `30` | 背景最多几条 |
| `llm.bg_chat_chars` | `2000` | 背景最多多少字（约 1000 token） |
| `llm.bg_chat_minutes` | `120` | 背景只认这么久以内的群聊，防止把旧话题当「刚才在聊」 |
| `llm.bg_chat_min_rows` | `6` | 「上次说话之后」不足这么多条就往前补（`0` = 不补） |

> 🧠 **为什么需要「群聊背景」**：群友闲聊存的是旁听记录（`kind='listen'`），
> 而问答历史是另一条通道（`kind='chat'`）——**两者不通用**。所以群里聊了半小时，
> 然后有人 @ 它问「刚才聊啥呢」，它其实一无所知。开了 `bg_chat` 之后，被动回答
> （@ / 戳一戳 / 发链接）会先把「**它上次说话之后**」群里聊的那一段带上（以
> `chat_log.id` 为界，不是时间戳——同一秒可能有多条），它就能接上前文。
> 这段走参考资料传，**不进对话历史**，也不占 `history_chars` 的预算；
> 代价是每次 @ 多约 1000 token。找不到「上次说话」的位置时（新群）回退到
> 「最近 `bg_chat_minutes` 分钟」。
>
> ⚠️ **两个必须知道的细节**（都是「前言不搭后语」的真实来源）：
> ① **当前这句提问会从背景里剔掉**——群里的 @ 消息会被记两遍（旁听一条、问答一条），
> 不剔的话背景里会出现和提问一字不差的一句，而背景开头写着「不是在跟你说话」，
> 同一句既算「别人的闲聊」又算「问你的」，模型只能挑一个信。
> ② **界限之后不够 `bg_chat_min_rows` 条时会往前补**。它刚回完一句就被人 @ 的情形很多，
> 那时界限之后只剩这句提问本身，等于没有语境——表现就是「上一句还答得好好的，
> 下一句突然问我在说什么」。补一小段就能接上话题；不想要这个行为就填 `0`。

> 📄 **聊天记录是怎么读到的**：`forward` 段只是一个 id，要再调一次 `get_forward_msg` 才拿得到内容
> （`message_id` / `id` 两种参数名都会试），内联的 `node` 段直接解析。
> **嵌套转发只展开一层**——否则「转发了一堆转发」能无限膨胀。
> 展开的内容**只作用于这一次请求**，不写进上下文历史；读不出来一律静默降级，不会让群里没回应。
>
> 🌐 **网页链接不自动抓**：模型看到的只是一串 URL，要不要读、读哪个，由它自己决定——
> 需要时它会调用 `fetch_url(url)` 工具（见下面的「工具与技能」）。这样不会每条消息都去抓、
> 也不会把一堆无关页面塞进上下文。
>

### 工具与技能（tool calling）

模型不是只会说话的纯文本接口——它可以**自己决定**调用工具。当前内置：

| 工具 | 干什么 | 什么时候用 |
|---|---|---|
| `fetch_url` | 抓网页正文并抽成纯文本；长文可带 `prompt` 按问题摘要 | 有人发了链接、它需要知道里面写了什么 |
| `web_search` | 搜网页，返回几条「标题 — 摘要（网址）」（默认关闭） | 问的是新闻、价格、比分、谁的现任职位、软件最新版本这类会过时效的事 |
| `list_skills` | 列出已安装技能的名字 + 简介 | 遇到不熟的任务，先看有没有现成方法 |
| `use_skill` | 读某个技能的完整说明 | 照技能里的步骤做事 |
| `read_skill_file` | 读技能目录里的附加文件（`references/xxx.md`） | 技能正文让你「读取 references/…」时；一次一个文件 |
| `run_skill_script` | 跑技能自带的脚本（默认关闭） | 技能说明里明确要求跑脚本时 |
| `remember` | 把关于某人的长期事实记进档案 | 对方说到偏好、身份、习惯，以后会用得上 |
| `recall` | 查某个人的完整档案（不填人则看全群一览） | 拿不准谁是谁、想确认自己记过什么 |
| `forget` | 删掉档案里记错的条目 | 记错了、对方纠错、信息过时 |

前四个是「只读 / 只抓」，后三个是**唯一允许写文件**的通道，而且只能写 `data/memory/`。

抓取由 [trafilatura](https://github.com/adbar/trafilatura) 负责正文抽取（不手写正则）。
安全上只放行 **http/https 的公网地址**：内网 / 环回 / `169.254.x` 一律拒绝，重定向
**逐跳复核**——否则一条 `http://内网/redirect` 就能读到云元数据。这套叫 **SSRF 防护**。

三处细节让它不至于「明明有内容却说打不开」：

- **正文抽不出就退回页面元信息**。B 站、知乎这类页面正文是 JS 渲染的，trafilatura
  往往只抽出标题（实测 B 站视频页只有 31 字），以前会被判成「没抓到」；现在改用
  `<meta description>` / `og:*` 兜底——那里通常写着简介、播放量、作者，够回答
  「这个视频讲什么」。
- **图片 / PDF / 音视频会明确说「读不了」**。以前统一返回「抓不到」，模型会换个说法
  反复重试同一个图片地址，或者跟群友说「网络打不开」。现在直接告诉它是哪一类、
  别再抓。
- **被站点反爬拦下时单独说明**。B 站、知乎对机房 IP 会返回 `412` / `403` / `429`。
  这和「页面不存在」是两件事：前者重试没用、该换来源或请人贴原文，后者才是地址错了。
  分开说之后模型不会一直重试同一个地址。
- **同一链接 15 分钟内只真抓一次**（`llm.fetch_cache_minutes`）。群里一个链接常被几个人
  先后贴上。

另外，长网页可以**按问题摘要**：模型调 `fetch_url` 时带上 `prompt`（例如「散热怎么样」），
正文超过 `llm.fetch_summarize_chars`（默认 4000 字）就先让模型按那个问题摘一遍，而不是
把前 2000 字硬塞给它。贴一篇两万字评测问某个细节时，差别很明显。代价是多一轮模型调用。

同一轮里模型可能要连调几次工具（先抓网页、再查技能），每次结果以 `role: tool` 回填，
最多 `tool_rounds` 轮；**最后一轮不带 tools**，强制它给出正文，避免「一直要工具、
最后什么都没说」。接口若不认 `tools`（有些中转只转发 `messages`），会自动去掉工具
重试一次——少个功能，但机器人不会哑。

> ⚠️ **最后一轮的副作用**：`tools` 一撤，模型就没法结构化地调工具了；它要是还想搜，
> 只能把内部语法当文本写出来（实测 DeepSeek 会吐
> `<｜｜DSML｜｜ invoke name="web_search">` 一整段）。所以出口有两道闸：
> `llm.strip_tool_marks()` 把这类标记块整段剥掉；剥完如果什么都不剩，就**再要一次正文**
> （仍然不带 tools，并明确禁止写调用语法）。这也正是 `tool_rounds` 默认给到 `5` 的原因——
> 3 轮时经常「差一口气」正好卡在最后一轮。

#### 技能包（SKILL.md）

在 `data/skills/` 下建一个目录，放一个 `SKILL.md`：

```
data/skills/noodle/
├── SKILL.md
└── scripts/            # 可选，配合 llm.skill_scripts 使用
    └── timer.py
```

```markdown
---
name: noodle
description: 煮面条的标准步骤与常见问题
---

1. 水开再下面条，煮三分钟；
2. 捞出过凉水，拌芝麻酱。
```

- 模型先 `list_skills` 看「名字 + 一句话简介」，觉得用得上才 `use_skill` 读全文
  ——这是**渐进披露**，不会一上来就把所有技能正文塞进上下文。
- 加技能就是丢一个目录进去，**不用改代码**（每次请求现扫，不必重启）。
- 🔒 **QQ 聊天里禁止安装任何技能**。这不是配置项、也没有开关，三道闸一起拦：
  1. 工具名有硬白名单（`fetch_url` / `list_skills` / `use_skill` / `read_skill_file` / `run_skill_script`），
     就算以后有人加了「安装技能」的工具，也不会被送到群里；
  2. 模型自己编出 `install_skill` / `write_file` 这类名字时，工具调用会被直接拒绝，
     并回一句「聊天里装不了，需要管理员放目录」；
  3. 系统提示词末尾由代码追加能力边界（用户改人设也删不掉），模型一开始就知道
     自己装不了，不会假装装好了。
  所以**唯一的安装方式**就是管理员自己在服务器上把目录放进 `data/skills/`。
- `llm.skill_scripts` 打开后模型可以 `run_skill_script` 跑技能目录里的 `.py` / `.sh`：
  只能跑**已存在**的脚本（模型不能写文件）、参数最多 8 个、超时默认 20 秒、
  输出截断 4KB、最小环境变量（不把 API Key 漏给脚本）。**默认关闭**——
  一开就是「模型可以让你服务器上跑技能目录里的代码」，只该在完全信任技能来源时打开。
- 脚本执行**不能用来装技能**：跑之前给技能根目录做快照，跑完比对——新增的文件删掉、
  被改被删的写回原样、新建的空目录清掉，并把「动了技能目录」这件事写进日志和工具结果。
  （`skills_dir` 若指到了含数据库的目录，守卫会自动跳过，免得把库写回去。）

> 🧠 **思考模式怎么选**：默认 `thinking: auto` 就是「不管，用模型自己的默认行为」，绝大多数情况够用。
> 需要更省更快就选 `low`，要它想清楚点选 `high`。写法由 `thinking_style: auto` 自动判断：
> 通义 / 百炼 → `enable_thinking` + `thinking_budget`；GLM / Claude / OpenRouter → `thinking: {type, budget_tokens}`；
> OpenAI 官方与 Azure → `reasoning_effort`；DeepSeek → `thinking` 开关 + `reasoning_effort`；
> Moonshot 这类靠模型名区分思考的 → 不发参数。
>
> ⚠️ **DeepSeek 的自动识别在「中转 / 本机地址」下会失效**（域名里没有 deepseek），
> 只能靠模型名。所以用中转时请把 `thinking_style` 显式写成 `deepseek`，
> 否则档位不会下发——网页状态区会提示「当前写法不发思考参数，档位不会生效」。
> DeepSeek 侧的档位映射：`low`→low、`medium`→high、`high`→high、`max`→max（它只认这三档），
> 并且**不接收 `thinking_budget`**（那是 Anthropic 风格的参数，发过去也没用）。
>
> ⚠️ **思考模式开启时，`temperature` / `presence_penalty` / `frequency_penalty` 不生效**
> （官方说明：不报错、也不生效）；`top_p` 对 `deepseek-flash` 只在思考模式下有效，且范围是 `0.95~1.0`。
> 想靠调温度改变说话风格，得先把思考关掉（`thinking: off`）。
>
> 猜错就在 `extra_body` 里手写，例如 `{"enable_thinking": true}` 或 `{"reasoning_effort": "high"}`。
>
> ⚠️ **开了思考必须同步调大 `max_tokens`**：思考的 token 与正文共用这个额度，`max_tokens: 512` 配上
> `high` 很容易「想完没得写」——表现为模型返回空内容，网页操作日志里会直接这么报。
> 网页「机器人」页的**实际请求参数**（可展开）会把最终发出去的 `thinking` / `reasoning_effort` / `max_tokens`
> 全列出来，改完先看一眼就不会白折腾。
>
> 🧯 **上下文不会无限膨胀**（三层保护）：
> ① `history_rounds` 控轮数（最多 2 万轮）；② `history_chars` 控**总字符**（默认 3000，超出从最旧的成对丢弃）；
> ③ 单条历史封顶 `history_item_chars`（默认 2000 字）、系统提示词封顶 4000 字。
> **真正决定「记得多长」的是 ②**——两道闸谁先到头谁生效。
>
> 📏 **窗口能开多大（实测数据）**：deepseek 系列中文约 **2 字 / token**，窗口上限
> **1,048,576 token**（超了会报 `prompt is too long: … > 1048576 maximum`）。
> 实测 200 万汉字 = 947K token 仍能过，250 万汉字就会 400。所以 `history_chars`
> 最多填 2000000，**留出输出与档案的余量后建议 1200000 左右**（约 60~80 万 token）。
> 代价是每轮请求都要重发全部历史：80 万 token 的输入处理约 10~15 秒，群里会明显变慢；
> 想「记得久又要快」，更好的做法是靠下面的**人物档案**而不是把窗口塞满。
>
> 💾 **上下文现在会落库**：每轮问答写进 `chat_log` 表，进程重启后第一次发请求时
> 自动从库里恢复（日志里是 `从库里恢复 N 条历史`）。保留天数由 `llm.history_days` 控制。
>
> 就算服务端仍然报「上下文超长」，程序会**丢掉该群历史后自动重试一次**（日志里是
> `上下文超窗（丢弃 N 条 / M 字）→ 不带历史重试`），不会让群里看到一串报错。
>
> 📊 **「上下文用量」一眼可见**：网页「机器人」页有一张用量卡，按群统计一次请求的窗口
> 被谁占了——**系统提示词（人设）/ 群记忆档案 / 能力边界规则 / 工具与技能 / 对话消息**
> 五段，各带 token 数与百分比，顶上是大字百分比和一条分段进度条。
> 分母是 `llm.context_window`（默认 1048576），**它只管这条进度条**，不参与请求、不影响裁剪。
> token 数是估算（中文 2 字/token、英文与 JSON 3.5 字符/token），够看趋势、不必当真值。
> 想知道「平时发一句到底花多少」，把群切到「不选群 · 空会话基线」——那就是没有历史时的开销。

### 群记忆（机器人记人）

对话上下文记的是「刚才聊了什么」，群记忆记的是「**这个人是怎样的**」——跨对话、
跨重启、跨月份。两套东西互补：前者受窗口限制，后者落在磁盘上，人多了也不会爆。

**它是怎么工作的**

1. **旁听**：机器人把群里每条文字消息记进 `chat_log(kind='listen')`，**只记录、不回复、
   不影响任何流程**。不旁听的话它只看得见 @ 它的那几句，等于记不住人。
2. **整理**：每隔 `memory.digest_hours`（默认 6 小时）把这些新消息交给模型，让它归纳出
   「每个人的稳定特征」，写进档案；也可以在网页「🧠 群记忆」页点「立即整理」手动跑。
3. **注入**：每次回复时把群概况 + 风格卡 + 成员档案摘要拼进系统提示词（在人设之后、
   能力边界之前），所以模型一开口就知道谁是谁、也知道这个群平时怎么说话。
4. **对话中现记**：模型还能主动调 `remember` 记下刚提到的信息，`recall` 翻档案，
   `forget` 删掉记错的。

**档案长什么样**（`data/memory/<群号>/people/<QQ号>.md`，可以直接编辑）

```markdown
---
uid: "123456"
nick: "小明"
aliases: ["小明", "明哥"]
first_seen: "2026-10-01 12:30"
last_seen: "2026-10-23 21:10"
msgs: 128
---

- 2026-10-20 喜欢周杰伦，常点《七里香》
- 2026-10-22 在杭州读大三
```

群层面的共识（黑话、群规、内部梗）单独放在 `data/memory/<群号>/group.md`。

**几个刻意的取舍**

- **只写素材里出现过的人**：整理时如果模型编了个 QQ 号出来，会被丢掉——幽灵档案比没有档案更糟。
- **整理失败不消耗素材**：模型没按 JSON 回答时不标记「已整理」，下一轮还会重试，
  不会因为一次抽风就把那段聊天永久跳过。
- **单人档案有上限**（`memory.note_chars`）：到顶后新记录会挤掉**最早**的条目，
  并把「挤掉了几条」告诉模型，免得它以为自己记下了全套。
- **注入有预算**（`memory.inject_chars`）：人多时按最近活跃截断，并注明「还有 N 人没装进来，
  需要时用 recall 查」——模型知道有人没看到，就不会把人记混。
- **只记稳定的东西**：身份、职业、所在地、兴趣、说话习惯、常用梗。不记一次性的事，
  也不记密码、手机号、住址这类敏感信息（提示词里明确要求，档案也在你自己手上，随时可改）。

> 🔒 **这是模型唯一能写的地方**。技能目录、项目代码、`data/` 下其它文件都写不了；
> 记忆路径由代码拼死（`data/memory/<数字群号>/people/<数字QQ号>.md`），
> 模型只能给「谁」，给不了路径，所以没有目录穿越这回事。
>
> 🧹 **隐私与清理**：不想让某个人被记，在「群记忆」页删掉他的档案即可（或直接删文件）；
> 想整体关掉就把 `memory.enabled` 关掉（不旁听、不注入、也不给记忆工具），
> 已有档案会原样留在磁盘上。群聊记录保留 `memory.keep_days` 天（默认 180）。

### 说话方式（风格卡）

档案记「谁是谁」，风格卡记「**这个群怎么说话**」。这是两件事，粒度和用途都不同：
「喜欢周杰伦」是事实，「常一句一换行、句尾不打句号、爱用『。。。（三个句号）』」是语体，
后者才是「像人」的来源。

**它凭什么比形容词有用**：写「语气活泼」模型基本无感；给它五条真实原话
（「绷不住了属实是」「？你认真的吗。。。」），它立刻就能对上频道。所以卡的核心不是描述，
是**样本**。

**怎么工作**

1. **采样**：从旁听记录里挑 `memory.style_days`（默认 30 天）内的消息，滤掉链接、分享卡片、
   纯标点、超长段落，再按**每人配额**（`style_per_person`，默认 6 条）等间隔抽取。
   配额是为了防「话痨刷屏」——不设它，风格卡会变成群里最活跃那个人的口癖合集。
2. **蒸馏**：每 `style_hours`（默认 24 小时）把素材交给模型，要它输出句长、标点、高频词、
   少用的表达，以及 6~10 条**逐字原话**。没给够 3 条原话的一律判为无效，**不覆盖旧卡**。
3. **注入**：风格卡有独立预算 `style_chars`（默认 800 字），排在群概况之后、成员档案之前，
   **不占人设的 4000 字**，也不挤占成员档案的额度。

**卡长什么样**（`data/memory/<群号>/style.md`，可以直接编辑，改完保存即生效）

```markdown
- 句长：多数 8~15 字，常一句话一行
- 标点：句尾基本不打句号，爱用「。。。」和「？？」
- 高频词：绷、乐、属实、寄
- 少用：首先/其次这类书面连接词、客服腔

群友原话（学语感用，别复述内容）：
1. 绷不住了属实是
2. ？你认真的吗。。。
3. 这歌有点东西
```

**几个刻意的取舍**

- **整卡重写，不追加**：追加式记忆半年后会变成一堆自相矛盾的形容词，还越写越长。
  旧卡轮转进 `style.v1.md`～`style.v3.md`，随时能翻。
- **失败绝不覆盖**：模型没回、不是 JSON、原话不够，一律保留旧卡——旧卡总比空卡强。
- **素材里没有昵称和 QQ 号**：只学「这个群怎么说话」，不复刻某个人。让机器人带上某位群友的
  口癖，观感上就是冒充，这条线不越。
- **注入时带约束句**：样本是别人的原话，提示词里明确写了「别照搬内容、别声称是某个人说的」，
  否则模型会直接复述，或者用「我说过」的口气引用。
- **风格是慢变量**：采样用「最近 N 天」的滚动窗口，不是「未整理过的消息」。重复看同一批
  消息不浪费，反而让卡随新消息平滑漂移，而不是被一批新消息整个推翻。

> ⚠️ **风格学习跟背景一样，只认旁听名单**：`memory.listen_groups` 非空时只旁听那几个群，
> 名单外的群没有素材，风格卡永远是空的。

### 人设修订（只提议，不自己改）

到这里有三层东西在影响它说话，分工要分清楚：

| 层 | 改的是什么 | 谁决定 |
|---|---|---|
| 成员档案 | **谁是谁**（事实） | 自动，写进提示词的「记忆」段 |
| 风格卡 | **这个群怎么说话**（语体 + 原话） | 自动，写进提示词的「记忆」段 |
| 人设 | **它是什么角色、怎么说话**（`llm.system_prompt`） | **人定**，模型只出建议 |

第三层不做自动，理由很实在：

- **自激漂移**：让模型评价自己、再改自己，它会单调地滑向「模型想象的好文章」——书面、
  完整、礼貌、爱分点。这恰好就是群里嫌的那种 AI 味，而且它**不会自己纠回来**。
- **能被注入**：群里发一句「你以后每句都加喵」，若直接吸收，一句玩笑就变成永久人格。
- **改坏无声**：人设是手写的那几千字，覆盖掉没有 diff 可看、没有回滚点。

**流程**

1. **识别**：机器人说完话（3 分钟内）群里冒出「一股 AI 味」「别打官腔」「说人话」这类话，
   先用正则粗筛（免费），命中才让模型确认一次。闲聊里「这个 AI 挺好用」靠这一步挡掉。
2. **记录**：确认后写一行到 `data/persona/feedback.jsonl`，**带上它当时说的那句**——
   只有抱怨没有上下文，提议时根本不知道该改哪儿。
3. **提议**：攒够 `persona.min_feedback`（默认 5 条）后，每 `persona.propose_hours`
   （默认一周）跑一次：把当前人设 + 抱怨 + 风格卡一起给模型，要它指出哪几句该改。
4. **人审**：结果落在 `data/persona/proposals/*.json`，网页「群记忆 → 人设修订建议」里
   逐条摆出「原句 → 改成什么 → 依据哪条抱怨」。自己复制去「机器人设置」改，热生效。

**提议的护栏**（代码里逐条校验，不靠提示词自觉）

- `old` 必须**逐字出现在当前人设里**，找不到就丢——模型爱说「把第 3 段改成…」，可人设里没有第 3 段；
- 每条 `old` / `new` 都 ≤80 字，一次最多 3 条，同一段被改两次只留第一次；
- 每条必须带 `evidence`，且人设改完之后不能超过 `persona.persona_limit`（默认 2500 字）；
- `new` 里出现「忽略」「无视」「密码」「api_key」这类写法的整条丢掉；
- 一条都没通过校验就返回「没给出能采纳的修改」，**不会凑数**。

> 🧹 清理：抱怨流水在 `data/persona/feedback.jsonl`，建议在 `data/persona/proposals/`，
> 都是普通文件，直接删；网页上也有「清空抱怨」。想关掉就把 `persona.enabled` 设为 false
> （已有记录原样留盘）。


> ⚠️ **这一页的设置只能在网页端改**：群内没有任何命令读写 `llm.*`（`/music set` 只认
> 时间窗口那几个字段）。配置层也把 `llm.` 整段列为**进程级设置**、不允许「按群覆盖」——
> 否则会出现「给某个群改了 base_url、但 `llm.groups` 里没包含它」这种谁也说不清的状态。
> 想让某个群单独一套模型，请直接部署第二个实例。

> 💡 兼容任意 OpenAI 协议的服务：DeepSeek（`https://api.deepseek.com/v1`）、
> 通义 / 智谱 / Moonshot / one-api、本地 Ollama（`http://127.0.0.1:11434/v1`）、vLLM 等，
> 只要 `base_url` + `api_key` + `model` 三项填对即可。Ollama 这类不需要 Key 的服务，
> `api_key` 随便填一个非空值占位（留空会被判为「没配置好」而不启用）。

### 收集预览与实时操作

面板里「📊 收集预览与实时操作」卡片可随时查看并干预收集，无需进群敲命令：

- **预览**：按窗口展示每个群收集了哪些歌（序号 / 歌名 / 歌手 / 分享者 / 平台 / 是否匹配网易云），
  顶部可切换不同窗口、显示网易云登录态。
- **实时开关**：`强制开始收集` / `强制停止收集` / `恢复自动` —— 等价于 `/music collect on|off|auto`。
- **归档**：`归档本群` 立即把某群建歌单；`归档当前窗口全部` 批量归档当前窗口所有群。
- **删除歌曲**：勾选表格里的歌曲 → `删除选中`；`清空本窗口` 清空该群本窗口全部记录。
- **预览**：`预览歌单名` / `预览简介` 先看这一期会生成什么，再决定是否归档。

> 所有操作都走 `MUSIC_WEBUI_TOKEN` 鉴权；归档/删除会直接写库或调网易云，**请确认后再点**。

> ⚠️ 安全：机器人 `HOST=0.0.0.0` 时 8080 暴露在所有网卡，WebUI 仅靠 `MUSIC_WEBUI_TOKEN` 保护，
> 务必设置强令牌，并让服务器防火墙**不要**对公网开放 8080 端口。

## 猜歌小游戏

玩法：**猜每首歌是谁分享的**。每首歌一张卡片（带网易云播放器），玩家按顺序排出
3 个自己认为最可能的分享者；命中第 1/2/3 位分别得 3/2/1 分，全部歌曲累加就是总分。

**一次只答一首**：全员同时答当前这一首，**都答完（弃答也算）才自动翻到下一首**，
最后一首答完自动开牌。没答完时页面上只显示「还有 N 人未答」这个人数字 ——
谁交了属于猜身份的线索，不列名字。有人掉线/挂机时房主可以「跳过这首」。

- 玩家页面：`http://<主机>:8080/guess`
- 名单管理：`http://<主机>:8080/music-admin/guess`（侧边栏「🎲 猜歌名单」也能进，用管理令牌）

### 登录方式

白名单 QQ 号 + 机器人发的**一次性验证码**，两条取码路径：

1. **网页点「发验证码」**——机器人主动私聊推给你。这条路**要求先加机器人为好友**：
   实测 NapCat 对非好友的 `send_private_msg` 一律返回 `retcode=1200`，
   带 `group_id` 走群临时会话也一样被拒，群设置里的「允许发起临时会话」救不了。
2. **在 QQ 里私聊机器人发「登录」**（推荐给群友）——你主动开口，会话就已经建立，
   机器人直接在**这个会话里**回码，不要求好友关系。关键词：登录 / 登陆 / 登入 /
   验证码 / 猜歌 / login。

拿到码后回网页填，登录态默认保留 30 天。

> 第 2 条是主力：群友不用挨个加机器人好友。第 1 条留着是因为加了好友的人点按钮更顺手。
>
> 为什么不接 QQ 互联 OAuth：官方接口只返回 `openid`（应用内唯一，与 QQ 号没有可反推
> 关系），拿不到 QQ 号，与「按 QQ 号维护白名单、从群成员批量导入」对不上；而且网站
> 应用要备案域名 + 大陆服务器 + 实名审核。机器人本来就在群里，一条私聊码更直接。

### 名单

- **从群成员批量导入**：选群 → 拉取 → 落库（机器人须在线且在群里，走
  `get_group_member_list`）。
- **粘贴导入**：一行一个，支持 `123456789 小明` / `123456789,小明` / 只有号码。
- 支持停用（保留记录但不让登录）与删除；改动立刻生效，不用重启。

`game.whitelist_only` 关掉后任何 QQ 号都能进（只建议本地调试时这么干）。

### 房间

- 单人：自己一局，从任意历史窗口取题。
- 多人：建房得 6 位房间号，链接 `…/guess?r=ABC123`，把链接或房号发给朋友即可加入。
- **房主**可以转让；房主退出时由**在座玩家里最早加入的**那位接任（不是按列表下标）。
- 房间**没有人在**或 **`room_idle_minutes`（默认 60）分钟无业务动作**就回收。
  注意：WebSocket 心跳**不算**动作，否则房间永远不会过期。
- 断线重连：同一个 QQ 带同一个登录态重新打开页面即恢复，已提交的答案还在。

### 题目

两种来源，房主在开始前随时可换：

1. **历史收集窗口**：选「群 → 窗口」，直接用那一期的歌和分享者当答案；
2. **现场收集**：全员（含房主）把分享链接贴进页面，服务端复用机器人的
   `detector` + 平台解析器解析，非网易云的歌还会顺手匹配一次网易云（否则卡片里
   没有播放器）。

同一首歌被两个人贴进去（含 QQ 音乐 / 网易云的同曲）会按「歌名 + 首位歌手」合并，
只留最早那条 —— 否则会出现两张一模一样的卡片却要求不同答案。

**开场会打乱顺序**：点「开始游戏」时，卡片顺序和候选池顺序各洗一遍。不打乱的话，
「候选池里第一个名字」和「第一张卡」在原始数据里是同一首歌，等于送答案。

### 有的歌放不出声？

三种原因，按概率排：

1. **VIP / 付费 / 已下架**（最常见）——内嵌播放器是网易云的公开外链页，**不带任何
   登录态**，这类歌必然不出声，只显示"暂时无法播放"。出题时会批量查一次歌曲详情，
   命中 `fee=1/4` 或已下架的卡片会打上 **VIP** 标签并写明原因，不会让人以为页面坏了。
   每张卡还给了两个出口：「去网易云听」跳网页版；「去客户端听」走
   `orpheus://<base64({"type":"song","id":"<id>","cmd":"play"})>/` 拉起本机网易云客户端并
   **播放这一首**（客户端里有会员就能放，**需要装了客户端**，没装点了没反应）。
   载荷必须 base64 + 带 `cmd:"play"`，点完还要等 5 秒左右客户端才真正开播。
   ⚠️ 老的 `orpheus://song/<id>/?autoplay=1` 在客户端 **3.1.42 实测无效**（只开窗口不播放），
   别再换回去。
2. **没匹配到网易云 id**——卡片上没有播放器，只有一句提示和外链。历史窗口里的
   QQ 音乐 / 酷狗分享偶尔会这样。进房间时会自动补做一次匹配（每房最多 30 首），
   匹配结果写回库里，下次就正常了。
3. **手机浏览器**——网易云的外链播放器在移动端经常退化成"打开 App"，不是坏了。

> 预览和作答阶段都不会下发分享者：接口快照里根本没有 `sharer` 字段，答案只存在
> 服务端，结算时才随结果一起返回。前端藏字段是藏不住的，F12 一看就没了。

### 结算

- 最后一首**全员答完**后自动开牌（不是「交一次卷」——是逐题推进到末尾）。
- 排行榜同分**并列同名次**（1,2,2,4），不按提交时间破平。
- 明细里列出每首歌的真实分享者、每个人排了谁、每题得分。
- 单人模式每答完一首自动进下一首，答完最后一首立刻结算。
- 「跳过这首」只跳过当前一首（没答的人这首记 0 分），走到末尾同样自动结算。

### 归档

「现场收集」的那批曲目，结算后房主可以一键归档成网易云歌单，复用收集机器人的
`Archiver`：同一套匹配、命名模板与「谁分享了什么」简介清单，歌单窗口键是
`GAME-<房间号>`，与 `W/D/O` 开头的收集窗口互不干扰。匹配不到的歌会列出来，不静默丢。

`game.archive_by_host` 关掉后房主不能归档。

### 配置

`game` 段（网页端「配置 → 猜歌小游戏」也能改）。这一段是**进程级**设置，
不支持按群覆盖：

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | true | 总开关，关掉后 `/guess` 与接口都 404 |
| `whitelist_only` | true | 只允许名单里的 QQ 号 |
| `allow_single` | true | 开放单人模式 |
| `max_players` | 20 | 单房人数上限 |
| `room_idle_minutes` | 60 | 无业务动作多久回收房间 |
| `code_ttl_minutes` | 10 | 验证码有效期 |
| `session_days` | 30 | 登录态有效期 |
| `dm_group` | 0 | 发验证码时用来发起**群临时会话**的群号；0=自动（名单来源群 → 第一个有歌的群） |
| `guess_slots` | 3 | 每题排几个分享者 |
| `scores` | [3,2,1] | 命中第 1/2/3 位的得分 |
| `live_limit_per_min` | 10 | 现场贴歌限频（防刷解析接口） |
| `archive_by_host` | true | 房主能否归档 |
| `public_base_url` | 空 | 生成分享链接用的对外地址 |

> 房间状态在**内存**里：机器人重启，进行中的房间就没了（名单与登录态在库里，不受影响）。

## 歌单命名与简介模板

通过占位符渲染，未知占位符原样保留不报错。

| 占位符 | 含义 | 示例 |
|--------|------|------|
| `{seq}` | 自增期号 | `86` |
| `{slash}` | 年月日 `/` | `26/8/7` |
| `{yy}{m}{d}` / `{mm}{dd}` | 年月日 | `26` `8` `7` / `08` `07` |
| `{ymd}` / `{dot}` | 日期 | `2026-08-07` / `26.8.7` |
| `{week}` | ISO 周数 | `32` |
| `{weekday}` | 星期 | `周五` |
| `{window}` | 窗口区间文案 | `本周` |
| `{start}` / `{end}` | 窗口起止日 | `2026-08-03` |
| `{count}` | 实际收录首数 | `12` |
| `{total}` | 分享总数 | `15` |
| `{sharers}` | 参与人数 | `4` |
| `{group}` | 群号 | `123456` |

示例：`/music name Wk.{seq}线上学习{slash}` → 歌单名 `Wk.86线上学习26/8/7`

简介 = `desc` 模板开头 + 「谁分享了什么歌」清单，**一首歌占一行**：

```
Wk.86 线上学习歌单，共 12 首。

张三 分享《起风了》- 买辣椒也用券
张三 分享《晴天》- 周杰伦
李四 分享《海阔天空》- Beyond
```

`sharer_style` 可选 `list`（逐首列，默认）/ `by_person`（按人聚合）/ `by_name`（只列分享者名，每行形如 `1.张三`）/ `none`（不附）。

### 归档复用与分享即归档

- **同窗口复用**：同一窗口（如 `W20260824-0000`）归档过一次后再归档，会**复用已有歌单**只追加新歌，不会新建歌单；期号 `seq` 只在**新建歌单**时消耗。没有新歌时返回「歌单已是最新」。
- **复用也能改名**：复用时若显式指定了歌单名（`/music archive <名字>` 或配置页的「一次性歌单名」`pending_name`），会把已有歌单**真的改名**成该名字（改完读回校验），随后清空一次性名；不指定名字时沿用歌单的真实名字，不再显示「群歌单 窗口标签」这种占位名。
- **配置热重载**：`data/config.yaml` 被网页端 / 别的进程 / 手工编辑改动后，运行中的进程会自动重载；写配置时只覆盖本次改动的那一项，不会把内存里的旧配置整份写回去（避免把别的实例刚写好的期号、模板一起回退）。
- **分享即归档**：配置 `playlist.auto_archive_on_share: true`（默认 `false`）后，每收到一批新歌分享会立即自动追加进当前窗口歌单，跨平台来源会自动匹配网易云曲库。该行为**静默执行**（结果只在日志记录，不额外刷屏），适合"边分享边建歌单"的实时场景；未登录网易云时自动跳过。
- **期号自增对所有归档路径生效**：`seq` 只在「新建歌单」时 +1，而开启分享即归档后，本期歌单往往是**当周第一次分享**时就建出来的。所有归档入口（分享即归档、总库分享即归档、定时归档、网页端「同步到歌单」、总库归档）现在统一走同一段收尾逻辑，谁建出歌单谁负责消耗期号，不会出现「每周歌单名都是同一个数字、必须手动改」的情况。复用已有歌单时不会重复自增。

### 无法匹配的歌曲会当场提示

非网易云来源的歌（QQ音乐 / 酷狗 / 酷我 / Apple Music…）需要在网易云曲库搜一遍才能进歌单，搜不到时原先只能等到归档报告里才看到，分享者当场以为已经收进去了。

开启 `playlist.notify_unmatched: true`（默认开启）后，分享时会**立即预探测**一次：

- 搜到了 → 回填 `netease_id`，之后归档直接复用，不再重复搜索；
- 搜不到 → 歌照常收录进榜单，同时在「已收录」那条消息**同一条里**附一条提示（不额外刷屏）。

提示文案可自定义：`reply.unmatched_text`，可用占位符 `{title}` `{artists}` `{platform}` `{nick}` `{index}` `{count}` `{window}`。用自定义 `accept_text` 模板时，把 `{unmatched_line}` 放进模板即可（老模板里没写它的话，提示会自动补在消息末尾，不会丢）。

### 引用那条提示就能手动指定匹配

开启 `playlist.reply_match: true`（默认开启）后，**在群里引用**机器人那条带提示的消息、并贴上正确的网易云歌曲链接，就把这首歌绑定到该链接——分享者自己就能修，不用再找管理员去网页端点「手动匹配」。

- **谁可以**：管理员（超管 / 群管 / 群主）或**这首歌的分享者**；其他人引用只会收到一句提示（那条消息不会被当成新分享重复收录）。
- **只对尚未匹配的歌生效**：已经匹配到网易云的回一句「已经匹配到了」，不会覆盖（要改错的走网页端）。
- **命中后立即入库**：回填 `netease_id` + `matched`，歌名 / 歌手 / 专辑同步取自网易云详情；当前窗口仍在收集期且开了「分享即归档」时，会**后台把它补进本期歌单**（否则等下次归档 / 网页端「同步」）。
- **重启也有效**：机器人发出的提示消息 id 会落库（`song_notices` 表）而不是放内存，所以机器人重启、部署后引用旧消息照样认得。上线前发出的老消息没这个映射，引用会提示不出来（那条链接会被当作普通分享收录）。
- 文案可自定义：`reply.match_ok_text`（成功）/ `reply.match_fail_text`（失败）/ `reply.match_deny_text`（无权限），占位符 `{title}` `{artists}` `{matched_title}` `{matched_artists}` `{nick}` `{reason}` `{window}`。

### 同一用户本期只收录一首

开启 `playlist.one_per_sharer: true`（默认开启）后，**同一窗口内同一用户只收录第一首**，之后再分享的歌不入榜，只回一条提示。

判定基准是「**首次分享**」而不是「首次成功收录」：该用户本期发的第一条音乐分享就先占位（同一条消息里贴了多首时也只有第一首能过），占位记录落在 `sharer_claims` 表，按 `(群, 窗口, 用户)` 唯一，新窗口自动失效，并随定时清理一并回收。

**重复分享会归还名额**：如果这次占位的那首歌最后被判定为**重复**——总库已有（跨窗口去重命中）、
或当前窗口已有（别人先收了）——那它压根没进榜，名额会当场还给本人，他换一首新歌照样能收录。
（否则会出现「分享了一首总库已有的歌、机器人什么都没说，再分享别的歌却被拦『本期已经分享过』」。）
真正收录了才占住名额：在网易云搜不到、但确实进了本期榜单的歌，名额照旧算用掉。

**管理员删歌会释放名额**：在网页端「收集管理」里删掉某人本期的歌（勾选删除 / 清空本窗口），
对应的占位也会一并清掉，该用户可以重新分享（提示里带的还是首发歌名，不会停留在已删掉的那首）。
别人的名额不受影响；在「总库」视图里删歌不会误放某个具体窗口的名额。

**幽灵名额会自动回收**：占位里记着首发歌的平台 key（`sharer_claims.song_id`，老库启动时自动补列）。
每次判定「你已经分享过《…》」之前，都会先确认那首歌是否还在这 **窗口或该群总库**里——
两边都没有（说明管理员已经把它删了，无论删的是哪个视图、哪条路径，或是被清理任务带走的）
就把名额还回去、当作没分享过，不会出现「歌早删了却永远提示已分享过」。
歌还在库里（含同名同 key 被他人在榜、或在总库去重命中）时照旧拦，名额语义不变。

提示文案可自定义：`reply.sharer_limit_text`（默认「本期你已经分享过《{title}》了，要更换的话请找管理员」）。

| 占位符 | 含义 |
|--------|------|
| `{nick}` | 本次分享者（已套昵称映射） |
| `{title}` | 其本期**首发**的歌名 |
| `{artists}` `{platform}` | 首发歌的歌手 / 来源平台（平台已转中文名） |
| `{index}` | 首发歌在本期的序号；首发那首没进榜时为 `—` |
| `{count}` `{window}` | 本期已收录首数 / 窗口文案 |

关掉该开关即恢复原行为（同一用户可以继续分享多首）。

### 简介补写

写简介撞上网易云频控时会自动入队，由定时任务（`desc_retry_minutes`）或 `/music descfix` 补写。

补写时**按当前数据重新生成**简介，而不是重推存档的旧文本——否则期间删过歌、改过昵称映射、或歌单后来又追加了新歌，补上去的清单就会和歌单对不上。数据优先级：

1. 该窗口当前的收集记录（反映后续删歌 / 昵称映射变更）
2. 归档当时的快照（窗口被清空时用它兜底，清单不会变空）
3. 存档的旧文本（两者都没有时的最后退路）

### 收录回复模板

`reply.enabled: true` 后用 `reply.accept_text` 自定义「已收录」那条回复，群命令 `/music reply` 可随时改。

| 占位符 | 含义 |
|--------|------|
| `{index}` | 本期序号 |
| `{nick}` | 分享者（已套昵称映射） |
| `{title}` `{artists}` `{album}` | 歌名 / 歌手 / 专辑 |
| `{platform}` `{url}` `{duration}` | 来源平台 / 链接 / 时长 |
| `{artists_line}` `{album_line}` | 整行「歌手: xxx」「专辑: xxx」，无值时整行消失 |
| `{unmatched_line}` | 整行「网易云搜不到」提示，能匹配到网易云时整行消失（文案取自 `reply.unmatched_text`） |
| `{song}` | 歌曲详情块（歌名 + 歌手/专辑/来源/时长） |
| `{playlist}` | 当前群当前窗口的网易云歌单链接，未归档时用 `playlist_empty_text` 代替 |
| `{count}` `{window}` | 本期已收录首数 / 窗口文案 |

## 部署到服务器

> 完整「从零到运行」步骤（Docker / systemd 两条路线、NapCat 配置、验证、更新流程）见 **[`deploy/README.md`](deploy/README.md)**。
> 仓库已自带 **`Dockerfile`**、**`docker-compose.yml`**，以及裸机用的 **`deploy/start.sh`** 与 **`deploy/qq-music-collector.service`**。

要点：

1. **NapCat 与机器人必须能互相访问**（同机最省事）。机器人本身**不会连 QQ**，真正登录 QQ 的是 NapCat 协议端，得单独装；别把 WS 端口暴露到公网。
2. **时区大坑**：服务器多为 UTC，务必确认 `window.timezone: Asia/Shanghai`，否则定时全偏 8 小时。
3. **进程守护**：Docker 用 `restart: unless-stopped`；裸机用 systemd。
4. **字体**：纯净 Linux 镜像常没有中文字体，长图会变方块。Docker 镜像已内置中文字体；
   裸机 Debian/Ubuntu 用 `apt install fonts-noto-cjk`；RHEL/CentOS/Rocky/Alma（dnf 系）用
   `dnf install google-noto-sans-cjk-ttc-fonts`（或 `wqy-zenhei`）。
   **泰文**：歌单图片里若出现泰文昵称/歌名，主字体（CJK）不含泰文，需单独装泰文字体——
   Debian/Ubuntu：`apt install fonts-noto-sans-thai`；dnf 系：`dnf install google-noto-sans-thai-fonts`。
   装好后渲染会自动探测到，无需改配置；也可在 `render.thai_font_path` 显式指定。

### 方式一：Docker（NapCat 也是 Docker 时首选）

```bash
cp .env.example .env && nano .env      # 填 SUPERUSERS / ONEBOT_ACCESS_TOKEN
docker compose up -d --build
docker compose logs -f bot
```

⚠️ **容器网络坑**：NapCat 容器里的 `127.0.0.1` 指向它自己。反向 WebSocket 必须填
`ws://qq-music-bot:8080/onebot/v11/ws`（两个容器同网络时），三种网络场景见 [`deploy/README.md`](deploy/README.md)。

### 方式二：裸机三步（细节见 deploy/README.md）

```bash
sudo apt install -y python3 python3-venv fonts-noto-cjk
cp .env.example .env && nano .env          # 填 SUPERUSERS / ONEBOT_ACCESS_TOKEN
# 同机装好 NapCat，反向 WS 指向 ws://127.0.0.1:8080/onebot/v11/ws 并扫码登录
sudo cp deploy/qq-music-collector.service /etc/systemd/system/
sudo nano /etc/systemd/system/qq-music-collector.service   # 改 User= 和路径
sudo systemctl daemon-reload && sudo systemctl enable --now qq-music-collector
journalctl -u qq-music-collector -f
```

更新：`git pull && sudo systemctl restart qq-music-collector`。`.env` 与 `data/` 不进版本库，更新不动你的配置与数据。

## 注意事项

1. **weapi 风控**：网易云 weapi 接口在某些网络环境可能返回空响应，导致自动建歌单失败。遇到时用 `/music export` 导出文本手动建歌单。
2. **简介写入**：归档时通过 `playlist/update` 接口写入简介并保留歌单名（该接口有频控，失败会自动入队由定时任务补写，也可手动 `/music descfix`）。
3. **简介里的表情**：网易云简介按 utf8(3 字节) 存储，emoji 是 4 字节，带 emoji 的昵称会整条写不进去。默认 `emoji_style: text` 会把常见表情转成中文词（🎵→`[音符]`），不认识的 4 字节字符直接丢弃。
4. **音乐卡片签名服务**：协议端发原生音乐卡片时要向外部签名服务换 ArkShare 结构，那个服务经常 500。插件做了三级降级（原生卡片 → 自定义卡片 → 文字兜底），信息一定不会丢；同一平台连续失败 3 次会熔断 10 分钟，冷却期内直接走文字兜底。长期不可用就 `/music card custom`，或在 NapCat 配置里换可用的 `musicSignUrl`。
5. **跨平台匹配**：非网易云来源会在网易云搜索匹配；严格模式要求歌名与歌手都对得上，关闭后命中率高但可能加错版本。
6. **消息风控**：长图、@ 用户、音乐卡片都可能触发 QQ 风控，建议先在测试群验证。
7. **网易云写接口失败**：表现都是「简介写不上去」，但失败码含义不同 —— `code=301` 需要登录是 cookie 过期，开 `netease.auto_relogin`（默认开）会自动续期 / 账密重登并重试；`code=405` 操作频繁（**连 `linuxapi` 也回 405**）是写接口的账号级频控，重登没用，系统会直接入队、由补写任务隔一会儿重写（也可手动 `/music descfix`）。若日志出现 `code=8810 网络环境存在安全风险`，说明**服务器 IP 被网易云风控**，账密重登会被拒，只能在浏览器登录后复制新的 `MUSIC_U` 粘贴保存。账密在配置页「网易云登录」里填，或手动 `/music cookie`。
8. **多实例勿共存**：同一份 `data/` 只能跑一个 bot 进程，多实例会互相覆盖配置（期号、歌单名模板会乱跳）。改完配置记得重启，确保跑的是最新代码。
